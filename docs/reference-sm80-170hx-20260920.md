# SM80 / 170HX 参考项目复查（2026-09-20）

结论：下一轮应优先补齐 **TP 的图执行与多 token target 验证**，再处理 TP grouped MoE prefill。P2P 和 PLE RAM 是这条路线的基础，但本轮 P2P 实测只有约 3% 的 decode 收益，不能把对方约 170 tok/s 的成绩归因于驱动解锁。

参考对象固定为 [d73d8824a35a21dccd71e279f1f4442ee741eedf](https://github.com/nguyenthimy2022kg-alt/Qwen-Flash-SM80-170HX/tree/d73d8824a35a21dccd71e279f1f4442ee741eedf)，提交日期 2026-09-15。延续用户约束：原生引擎仅借鉴思路，不复制外部实现，不把对方输出当作正确性标准，不引入降低质量的量化或候选裁剪。本文初版为静态阅读；随后按用户要求，在隔离容器中完成了[复用现有 W4/W8 与 RAM PLE 的参考引擎实测](reference-own-w4w8-20260920.md)：非思考三轮均值 173.09 tok/s。该适配运行未修改原生 C++/CUDA 引擎。

## 本次已落实的基础

- 双 170HX 的 64 GiB BAR1 和双向 peer read/write 已独立验证；在完整模型显存占用下继续验证 P2P collective。
- 原 host-bounce 保留，新增显式 `--tp-transport p2p`；生产 stream 就绪后才读取 peer 输入，并等待两边读完才覆盖输入。scratch 和 event 按 group 复用。
- 新增 `--ple-storage ram`：原 FP8 payload 和 BF16 scales 全量加载到一份只读主机内存，两 rank 共享；SSD 仍为默认。两种方式使用相同查表、缩放、事务和采样语义。
- 实测、验证边界和运行命令见 [P2P 与 PLE 双模式交付记录](p2p-ram-20260920.md)。

## 优先顺序

| 优先级 | 本地缺口及具体改动 | 如何验证 |
|---|---|---|
| 1 | TP 当前是 eager，每 token 仍有 97 次 AllReduce；P2P 仍通过 CPU 配对和 stream 同步完成。先按层测 kernel launch、rank 等待、collective，再把不跨 collective 的固定计算片段接入 TP graph，后续评估通信与计算重叠。 | 同输入 raw logits、两个 rank 输出、重复 replay/reset、指针生命周期；单列 launch 次数、collective 等待和稳定 ITL。不可直接删除现有 producer/read-done 保护。 |
| 2 | TP 尚未接入 MTP。先实现双 rank 一致的 draft/verify/commit/rollback，再试 2/4/7 行 target 验证，减少每个发布 token 的权重读取和提交成本。 | 任意接受前缀、首个拒绝位置、拒绝后缀回滚、取消、context 尾部、两 rank 状态一致。先 greedy，再实现与 target 分布一致的 sampled speculative decoding。 |
| 3 | TP routed MoE prefill 仍逐 token 执行，因为各 rank 的 expert-grouped packed route 顺序不同。按原 token/slot 还原到共同布局后再规约，使两卡都能使用 grouped GEMM。 | 多 token、不同专家组合、空专家、不均匀负载和尾部；对照现有正确逐 token 路径的 FP32 partial 与最终 logits。 |
| 4 | 本地已有 HC GEMV/fused/grouped、PLE 投影/norm/residual 融合候选。先补全真机模型级门禁和逐项 A/B，不重复实现相同开关。 | CUDA fixtures 的逐位输出只是第一关；继续覆盖模型 raw logits、完整生成、bank/reset/rollback，并要求端到端收益。默认开启须有实测依据。 |
| 5 | PLE 可进一步把多个待验证 token 的行号提前规划、批量查表，复用 pinned staging 和 H2D 事件。RAM 模式已避免重复整表存储；是否只由一个 rank 查表再广播应实测，额外 collective 未必比两份小 H2D 更便宜。 | 使用不同历史而非重复热缓存，分别测查表、文件读取、H2D、首 token/尾延迟；保留每一代输入与消费结束的身份。 |

这是依赖关系与优先级判断，不是这些改动已经实现或已证明能达到指定速度。现有 PP MTP/graph 能力不能直接视为 TP 已支持；原生 TP 入口仍拒绝这些未接通的配置。

## 最新提交最有价值的同步经验

对方的 [TP PLE transport](https://github.com/nguyenthimy2022kg-alt/Qwen-Flash-SM80-170HX/blob/d73d8824a35a21dccd71e279f1f4442ee741eedf/src/tp_ple_transport.py) 使用 owner rank 的数据生产、专用通信 stream 和广播。关键约束是：

1. 通信必须等待当前 generation 的 staging 完成事件，不能仅看到 flag=1 就认定本次数据就绪，旧请求的 flag 可能仍为 1。
2. 缓冲复用必须等待广播读取及模型消费结束。
3. 其大 batch 路径在动态 CUDA/cuFile 调用前做 CPU rendezvous，避免另一 rank 提前提交等待型通信 kernel。112 的阈值来自对方图捕获配置，不适合直接抄成本地常量。

这些生命周期规则同时适用于 SSD 与 RAM。我们现有 P2P event/scratch 方案独立实现了 producer 就绪和跨卡读取结束保护；后续图捕获/异步化仍须保留这两个边界。

## 如何解释对方速度

对方 [启动配置](https://github.com/nguyenthimy2022kg-alt/Qwen-Flash-SM80-170HX/blob/d73d8824a35a21dccd71e279f1f4442ee741eedf/config/vllm-args.json) 组合了 TP2、expert parallel、MTP6、Marlin 和 FULL_AND_PIECEWISE 图执行。本地是独立 C++/CUDA runtime、混合 W4/W8/G128 artifact，当前 TP 基线为 plain eager，不能直接按相同硬件换算性能。

其 [性能记录](https://github.com/nguyenthimy2022kg-alt/Qwen-Flash-SM80-170HX/blob/d73d8824a35a21dccd71e279f1f4442ee741eedf/docs/%E6%80%A7%E8%83%BD%E8%AE%B0%E5%BD%95.md) 中，170.826 tok/s 的短提示长输出样本估算每轮发布 4.459 tokens、每轮约 26.097 ms。我们约 30 ms 才前进一个 token。因此多 token 验证是值得优先投入的方向；这个比较仅用于识别机制，不能推算实际收益。

其 8K～128K 测试是每档一次、未固定 seed、输出约 27K～37K token 的流式客户端计时。我们本轮是固定 prompt/输出预算、greedy、原生 RPC、重复三次。上下文、采样、artifact、接受率和计时口径均不同。

不采用完整词表 INT8 筛选再 top-32 BF16 复核方案：本地 output 已为 W8，不能重复获得从 BF16 转 W8 的同等收益；有限候选集可能漏掉真正 argmax，580 个历史输入一致不证明任意输入等价。也不因对方使用 GDS 就把 GDS 作为必要前提，256 GiB 主机上的完整 PLE RAM 是本次明确提供的可选路径。
