评估对象：[Qwen-Flash-SM80-170HX](https://github.com/nguyenthimy2022kg-alt/Qwen-Flash-SM80-170HX/tree/c9ee1ec0b4923f2fbb21c6e452dd3cc85c7c4ff6)，固定提交 `c9ee1ec0b4923f2fbb21c6e452dd3cc85c7c4ff6`。阅读公开源码、配置及性能记录，与当前本地实现对照；没有执行外部代码或修改 runtime。按要求略过 GPU 直连 SSD。

结论：有正向参考价值，尤其是 HC 专用 kernel、多 token target 验证和 sampled MTP；不是可整包移植的提速补丁。对方是固定 vLLM/PyTorch/Triton/TileLang 栈的 overlay，本项目是 standalone C++/CUDA、两段流水线和事务状态机。

## 可落地的增量

### 1. 优先：HC BF16 专用 GEMV 与融合

对方 `src/hc_gemv_kernels.py` 按长 K/短 K 选择行数和分块；`hc_gemv_runtime.py` 仅匹配 `(10240,336)`、`(10240,320)`、`(320,10240)` 等固定形状。历史记录有 TP2 普通 decode 74.55→80.02 tok/s，但不能外推到本项目。

本地 `cuda/cuda_backend.cu::prepare_hyper` 分开执行 group RMSNorm、mix_down、SiLU、mix_up、sigmoid、mix 和 inject。`cuda/q38_kernels.cu::cuda_gemv_bf16` 的 optimized decode 分支仅针对 W4/W8；HC 保留 BF16，走每输出行一个 block 的通用 kernel。

建议移植形状专用调度思想，以我们实际矩阵布局为准；优先短 K 多输出行共享输入，再评估长 K reduction 和 SiLU/sigmoid epilogue 融合。不能照抄 TP2 的 336 维打包，也不能把 reduction 顺序变化当成 bitwise 等价。验证需覆盖 HC 中间输出、目标 logits、完整 token 和数值误差。

### 2. 重要架构候选：多 token target 验证

对方 GDN 的 `_forward_core_fused_norm_packed` 路径可调用 `fused_gdn_decode_post_conv_mtp`，传递 `cu_seqlens`、`num_accepted_tokens` 和 state indices；配置使用 MTP6。该 CUDA op 由固定上游环境提供，本仓库的 Python 调用接口本身并非完整可移植 kernel 实现。

本地 `src/executor.cc::speculative_step` 显式以 `chunk_tokens=1` 调用事务执行；优势是提前拒绝、少做无效后缀，代价是未跨多个 target token 摊薄权重读取与提交开销。

建议新增可选 2/4/7 行验证，与现有逐行验证实测比较。必须为 GDN、QSA、PLE、HC 保留任意接受前缀的正确状态，并处理拒绝后缀、取消和 rollback。低接受率下批量验证可能更慢，不能直接替换现有策略。Adaptive 宽度策略最终可同时参考验证批大小和接受率。

### 3. 重要能力缺口：sampled MTP

对方公开长输出记录使用 temperature=1、top-p=.95、top-k=20、presence penalty=1.5，同时开启 MTP6。本地 `speculative_step` 遇到 `sampler.sampled()` 会直接 `decode_one()`，因此当前 MTP 加速只用于 greedy。

值得借鉴的是完整采样验证语义，而非移植它的 draft argmax 函数。需要逐前缀应用 penalties/top-k/top-p，保证目标分布、随机数和事务回滚一致。对方 `draft_int8_runtime.py` 限定非 probabilistic 草稿；这不意味着 target 也必须 greedy。实际 rejection sampler 来自其固定 vLLM 基线，本次未把未阅读的上游 sampler 当成已验证实现。

### 4. 条件性候选：草稿 head 筛选和复核

对方 `src/draft_int8_runtime.py` 对完整 BF16 head 创建额外 W8/G128 副本，先 Marlin 打分，再对每卡 top-32 候选用原 BF16 权重复核。580 个历史样本一致不证明任意输入下都保留原 head argmax；候选集可能遗漏真正最优 token。

本地 `tools/q38_quant_policy.py` 已将 lm_head 归入 W8/G128，`run_mtp_step` 与 target 共用量化 `output`。所以重复加 W8 副本没有同样的降带宽收益。若继续探索，应评估 draft-only 更低位宽筛选、候选原 W8 复核或 head GEMV+argmax 融合；这些属于新的实验，并非对方已证明对我们有效。target head 和正式验证不可被近似候选筛选替换。

## 已有覆盖与不宜直接移植的内容

- QKVZ/BA 合并：对方 `projection_kernels.py` 是 BF16、4 行输出、256 列分块、128 threads 的形状专用 GEMV，不是 Tensor Core GEMM。本地已有 GDN/QSA/shared expert 多投影融合入口，主要增量是 BF16 内核调度，而非再加一层融合开关。
- CUDA Graph：双方都有。对方 startup coverage 计数和固定 shape guard 值得借鉴；本地已有双 bank piecewise target graph 和 MTP graph，完整捕获还受状态指针和位置相关 QSA 限制。
- MTP6：本地宽度支持 1..64，6 是一个待测配置，不是缺失能力。
- GDN prefill：对方 SM80 自动选择 Triton chunk GDN；FlashInfer/CuteDSL 的代码存在不代表 SM80 在使用。chunkwise 算法可列为本地 resident GDN 的实验对照，不能据文件名认定直接兼容或更快。
- TP2/TEP2：对方每层双卡协作并依赖 GPU P2P；本地 cut-25 两段流水线、host boundary。改变并行方式涉及权重分片、collective 和事务状态所有权，应单独立项，不作为本轮局部移植。
- 对方使用 NVFP4/Marlin artifact，本地是混合 W4/W8/G128。不能直接搬权重、量化速度数字或 cubin 缓存。

## 性能证据边界

`docs/性能记录.md` 明确：8K–128K 每档一次、未固定随机 seed、输出约 27K–37K tokens，自然结束；prefill 为输入/首输出等待的客户端近似值，decode 为流式接收速率。短提示词 INT8 前后输出也不同，+8.1% 不是独立消融收益。

因此其 151–170 tok/s 说明这套组合值得研究，不证明任一补丁能使我们的 64-token、不同 artifact、不同并行配置达到同样速度。后续需固定 fixture/seed/output budget，分别比较 kernel、每验证轮耗时、每轮发布 token 数、接受率、端到端速度和数值质量。

建议顺序：完成已有真机 baseline → HC 专用 GEMV/融合 → 多行 target 验证 A/B → sampled MTP → 条件性 draft head 实验。Prefill 先对照已实现 tile、MoE、GDN profile，再决定是否投入另一套 chunkwise GDN。
