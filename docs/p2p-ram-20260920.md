# 双 CMP 170HX：P2P 测速与 PLE SSD / RAM 模式

日期：2026-09-20。目标：`hp-z4-server`，Xeon W-2235、256 GiB 主机内存、双 64 GiB CMP 170HX。当前驱动 610.43.02，内核 7.0.0-31-generic，CUDA 13.3，PCIe 2.0 ×4，双卡 BAR1 均为 64 GiB。

本轮完成当前 TP 引擎的显式 P2P collective、PLE 双存储模式和参考仓库复查。默认入口仍为 SSD；TP transport 默认仍为 host，P2P 需明确选择。TP 仍属于 eager/plain 实验路径，未接入 MTP、graph 或 durable recovery。

## 同条件整模型测速

最终二进制 `build/p2p-ram/q38-cuda-runtime`，同一 `q38-tp2-lowcomm` artifact、greedy、context capacity 262144、chunk 512、单并发、durability off。每个进程先用 256 个 token ID 42 预填充并生成 32 tokens 预热；每轮 reset，再 append 相同 256 tokens，固定生成 256 tokens，共三轮。每次运行生成的 256-token 序列完全一致。

| 模式 | 三轮 tok/s | 平均 tok/s | 排除首个 seed 后的平均 tok/s | 模型加载时间 |
|---|---|---:|---:|---:|
| host + SSD | 32.500 / 31.907 / 31.911 | **32.11** | 31.98 | 52.56 s |
| P2P + SSD | 33.603 / 33.119 / 33.061 | **33.26** | 33.13 | 52.56 s |
| P2P + RAM | 33.096 / 33.030 / 33.033 | **33.05** | 32.93 | 73.59 s |

这组 P2P+SSD 相对 host+SSD 平均高 3.6%；此前 P2P-only 二进制的独立三轮为 32.19→33.10 tok/s，提升 2.8%。因此结论为**约 3% 的小幅改善**，不是量级提升。固定 256-token prefill 约 1.11→1.06 s。

与历史 PP 38.5426 tok/s 的比较需要进一步限定：复查原始 `q38-z4-infer-20260920/decode_probe_256.json`，PP 为 plain、MTP width=0、graph replays=0，256 个输出全部为 token 42，结束 canonical=704；本轮 TP 输出包含 124 种 token，结束 canonical=512。因此历史 PP/当前 TP 并非相同 token 历史和专家/缓存负载，不能把约 14% 的账面差距当作受控 A/B 结论，更不能归因于 PP 开了 MTP/graph。下一轮应以同一版本、相同上下文和固定 teacher-forced token 序列测 PP/TP，再按层分离计算、collective 等待、CPU 调度及 stage boundary 成本。

本轮 RAM 比 P2P+SSD 平均低约 0.6%，没有证明进一步提速。测试重复相同历史，SSD cache 很热；完整 RAM 的收益是预加载后不再依赖随机文件读取，是否改善更大、更多样的历史和尾延迟仍需相应负载实测。

计时使用原生 RPC，包含首个直接取自 prefill logits 的 seed，另列稳定 decode 速度供比较；不含模型加载、HTTP/tokenizer 或长上下文。测试按固定模式顺序运行，不把几百分点差异视为统计显著性结论。诊断 logit 捕获另起进程，不混入测速。

诊断准备重新核对 READY、indexes、源身份和 extent，但复用了本会话已经完整哈希验证的不可变模型文件，没有每次重读约 211 GB 做 SHA。正常服务启动仍完整哈希验证。加载时间测于已有文件缓存的环境，不是冷 SSD 启动成绩。

## RAM 的实际行为

| 项目 | 实测 |
|---|---:|
| PLE FP8 payload | 51,200,245,760 bytes |
| BF16 row scales | 640,003,072 bytes |
| 表总量 | 51,840,248,832 bytes，约 48.28 GiB |
| RAM runtime 最终 RSS | 51,474,880 KiB，约 49.09 GiB |
| SSD runtime 最终 RSS | 约 2.03 GiB；实际命中负载仅缓存约 26.6 MiB 数据 |
| RAM 模式进程 VmSwap | 0 KiB |
| RAM 预热及三轮生成新增 PLE 文件读取 | **0 bytes / 0 operations** |
| SSD 相同负载新增 PLE 文件读取 | 27,926,528 bytes / 6,818 operations，合计两 rank |

`PleStore` 只加载布局指定的 PLE extent，不加载同一 shard 内无关权重。保留所有原 FP8 bytes 和 BF16 scales，不重新量化。预加载成功后关闭源文件 descriptor；后续行查找通过内存复制完成。两 rank 共享一个只读 store，各自 hash/异步 reader/事务状态仍独立。RAM metrics 按一份真实所有权统计。

预算默认 64 GiB，包含 payload 与 scales；先检查预算及 Linux MemAvailable，并要求额外最多 8 GiB 余量。内存不足、文件截断或读取错误会使启动失败，不静默切回 SSD。整表使用 owned anonymous allocation，不使用单纯 warmed mmap；也不对约 48 GiB 整表做 pinned/mlock，因此操作系统仍可能在内存压力下 swap。实测仅能证明本次进程 VmSwap 为零。

SSD 保留 `io_uring READ_FIXED + O_DIRECT` 和原有限 LRU。`--ple-cache-gib 8` 是每份 store 的上限，当前 SSD TP 两 rank 各一份，最大共 16 GiB，另有两份 scales。RAM 忽略该页缓存容量，只保留一份 payload/scales。`ple_ram_resident_bytes` 仅含 payload，scales 单列，二者相加才是表总量。`ple_physical_read_bytes` 表示文件读取字节，并不代表块设备实际读取量；RAM 启动通过 buffered pread 可能命中文件缓存。

## P2P 实现与验证

P2P 由 GPU kernel 读取两 rank 输入，在本卡 scratch 内完成求和或 token-major gather。每次 collective 先记录两个 producer stream 的 ready event，再读取 peer；两边均记录 read-done，等待 peer 不再读取输入后才写回。这样保护了延迟 producer、原地 gather 和下一轮输入复用。scratch/events 按 group 高水位复用。BF16 规约保持 RNE。

仍有 CPU rank rendezvous、输出 stream 同步和每 token 97 次 AllReduce。去掉 host bounce 不等于去掉这些同步点；不能把 collective 等待时间全部解释成 PCIe 传输时间。P2P 请求在任一方向不可用时会明确失败，不暗中回退 host。

已通过：

- macOS 与目标 Linux CPU runtime tests，包括 RAM 预算、BF16/FP8 行与 scale、一批非法行无部分写入、截断源文件后的 RAM 可读性、并发读取和异步 reader。
- Python 66/66，使用具有 NumPy 的环境；本机三项 HTTP 测试在放行沙箱回环端口后通过。
- 目标机 host 与 P2P collective regression：延迟 producer、in-place 多行 gather、BF16 RNE、device 恢复、200 次双 group 并发规约、大 F32/BF16 payload 和尾部、peer failure、双卡 router。
- 最终二进制三种配置共九次固定 256-token 生成逐 token 一致；全程零 executor failure / rollback、零 CUDA allocation failure。
- SSD/RAM 另起诊断进程，比较 prefill 及随后八次输出操作的 9 份完整 BF16 logits（每份 248,320 元素），SHA-256 全部一致；也与此前 host+SSD 的对应捕获完全一致。包含 seed 操作，因此不是九次独立重新计算的 logits。
- 本次冷启动后的 kernel journal 未发现 NVRM Xid、AER error 或 IOMMU fault。

这些是本次路径等价性验证，不替代官方模型的完整 teacher-forced 质量门禁，也不代表完成 256K 长上下文发布验证。

## 构建与切换

目标机目录：`/home/icy/Homelab/Qwen3.8-Flash-Next-Dual-GPU`。

```bash
make -j3 cuda-runtime BUILD_DIR=build/p2p-ram \
  CUDA_HOME=/usr/local/cuda CUDA_COMPAT=0

LD_LIBRARY_PATH=/usr/local/cuda/lib64 .venv/bin/python tools/q38_tp_launch.py \
  --ready /home/icy/models/Qwen3.8-Flash-Next-q38-cut25/READY.json \
  --tp-root /home/icy/q38-tp2-lowcomm \
  --runtime build/p2p-ram/q38-cuda-runtime \
  --state-dir /home/icy/q38-tp2-serving \
  --tp-transport p2p --ple-storage ram --ple-ram-budget-gib 64 \
  --port 30001
```

选择 SSD 时，把末尾存储选项改为 `--ple-storage ssd --ple-cache-gib 8`。退回 host collective 用 `--tp-transport host`。切换需重启 launcher；先确认 PID 对应 `q38_tp_launch.py` 再发 SIGTERM，launcher 会清理 runtime/sidecar，不能同时启动两份完整模型。

PP 的 `tools/q38_launch.py` 同样提供 `--ple-storage ssd|ram --ple-ram-budget-gib N`，native runtime 对应 `--ple-io direct|ram`。PP 沿用其 READY/runtime identity 校验规则，源码变化后需生成匹配身份；本轮没有改写原 PP READY，也没有做 PP 整模型 RAM 性能宣称。TP 使用四份 rank index 及当前源码独立生成身份。

旧 `build/te-repair/q38-cuda-runtime` 保留，新的 RAM/P2P 参数必须配合新版二进制。不要把原生 RPC benchmark 连接到 HTTP 服务拥有的 executor；测试使用独立 socket 和进程。

原始证据位于本机 `.artifacts/q38-p2p-ram-20260920/`、目标机 `/home/icy/q38-p2p-ram-20260920/evidence/`。`bench.py` 为本轮固定路径的可复现实验脚本，`*-timing.json` 含全部 tokens、逐轮耗时、初末 metrics 与进程内存信息。进一步优化优先级见 [参考项目复查](reference-sm80-170hx-20260920.md)。
